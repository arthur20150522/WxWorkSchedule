# 微信凌晨掉线稳定性调查

更新：2026-08-30 03:35（Asia/Shanghai）

## 目标与判定标准

目标是区分以下原因，并在不主动退出、点击、发送或改变网络身份的前提下取得可复核证据：

1. 腾讯/账号侧撤销登录态；
2. 项目或人工在本机杀死、重启微信；
3. 微信自身崩溃或内存压力退出；
4. Windows 会话、虚拟显示或电源状态变化；
5. 公网 IP、网卡或连接变化。

关键判据：

- 主微信 PID 和创建时间不变，界面由 `ok` 变为 `popup/login`：账号会话被撤销的强证据。
- 主微信 PID 消失或创建时间改变：本机进程退出、崩溃、被杀或重启，不归为腾讯同进程踢线。
- 状态变化同时出现 4688 `taskkill.exe`、应用控制审计或 bridge 硬恢复日志：本地控制动作。
- 状态变化同时出现会话、显示拓扑或 IP 改变：相应环境因素。

## 已确认事实

- 服务器是约 2GB 内存的 Windows Server 云主机，微信为官方签名的 Windows 客户端。
- 无实体显示器；当前有两个稳定的虚拟显示输出，微信和监控均位于活动控制台会话 2。
- 公网 IP 在已观察窗口内稳定；系统未配置 WinHTTP 或用户代理。
- 电源计划为高性能，无睡眠、休眠、异常重启或凌晨会话断开证据。
- 过去 60 天没有微信崩溃事件；2026-08-19 有一次 `RADAR_PRE_LEAK_64` 内存泄漏预警。
- Windows Defender 当天实际扫描时间为 02:12，并非约 03:00。
- 长期运行的任务管理器曾占用约 1.4GB 私有提交。关闭后系统提交量下降约 1.44GB，分页使用从约 3.5GB 降至约 2.1GB，瞬时换页由约 537 次/秒降至约 11 次/秒。
- 微信当前总工作集约 250MB、私有提交约 533MB；2GB 规格仍偏紧。
- 公网管理端口存在真实暴力破解和 Administrator 锁定记录。这是严重安全问题，但现有证据不支持它直接造成微信掉线。

## 项目内本地退出路径

Git 历史显示 2026-06-04 引入了微信定时关闭功能：

- 初版在指定时间调用 `/wechat-kill` 并记录日志；
- 随后改成从关闭时间到拉起时间之间，每 30 秒直接执行 `taskkill`；
- 后期的连续压制路径不记录每次成功执行，异常也被静默吞掉。

仓库默认关闭时间曾为 `03:00`，与现象时间高度吻合。但当前数据库及 2026-08-13 备份均为 `enabled=false`、`02:30→06:25`，所以不能仅凭代码默认值断言近期每次掉线都由该计划造成。

第二条自动退出路径是 bridge 的白屏硬恢复：当 UIA 节点数过少时执行 kill + relaunch。历史 bridge 日志至少出现过两次这类动作。

第三条已由受控实验闭环的退出路径是 PM2 进程树终止：bridge 通过子进程启动微信，旧 PM2 配置的 `treekill=true` 会在 bridge 重启或部署时沿子进程树执行 `taskkill /T`，从而连带关闭微信。2026-08-30 03:13:30 受控重启 bridge 后，03:13:32 Windows 4688 记录到 `taskkill.exe`，WMI 随即记录微信主/子进程以退出状态 1 停止；03:13:44 被动监控确认微信已不运行。这不是腾讯账号侧踢线。

已实施保护：

- 定时杀进程除数据库开关外，还必须显式设置 `ALLOW_WECHAT_PROCESS_KILL=true`。
- 白屏硬恢复默认只告警，必须显式设置 `ALLOW_WECHAT_HARD_RECOVERY=true` 才能杀进程。
- 每 5 分钟的后台自动恢复默认关闭，必须显式设置 `ALLOW_WECHAT_AUTO_RECOVERY=true` 才会连接 wx4py、置前或点击；人工 `/recover` 保留。
- bridge 使用独立 PM2 配置并设置 `treekill=false`，避免服务重启、崩溃恢复或部署连带终止微信。
- 当前三个环境门禁均为关闭状态。
- 人工关闭接口增加账号和来源 IP 审计。

PM2 修复已通过反向受控验收：微信恢复至主界面后主 PID 为 8624、创建时间为 03:16:08；03:19:47 重启 bridge，bridge PID 变为 2928，但 03:20:27 微信主 PID 和创建时间完全不变，界面仍为 `ok`。因此“bridge 生命周期操作导致微信退出”的路径已修复。

## 2026-08-30 凌晨观测与实验

自然观测窗口 02:45—03:12 未复现掉线：02:50、02:55、03:00:44、03:05、03:10 的心跳均为 `ok`，微信主 PID 一直为 4388；公网 IP、会话 2、双虚拟显示拓扑均未改变，也没有微信退出、WER、白屏硬恢复或热补丁执行事件。因为微信当晚 02:02 曾被重启，登录时长被重置，所以单晚未复现不能排除腾讯/账号侧的定时或风险控制。

03:13 的受控 bridge 重启则稳定复现了本地进程退出，并由 `taskkill.exe`、WMI 停止事件和 UI `not_running` 三类独立证据交叉确认。应用 `treekill=false` 后，同样的 bridge 重启不再影响微信进程或登录界面。

- 08:20:46 弹窗开始消失，08:21:01 主界面恢复为 `ok`；微信主 PID 仍为 8624、创建时间仍为 03:16:08，公网 IP、会话和显示拓扑均未变化。三个自动/硬恢复及进程终止门禁仍关闭，未发生项目恢复动作。这建立了第一轮干净观察基线：登录态通过重新认证恢复，但微信主进程从账号安全下线到恢复全过程都未退出。

因此已经确认两类独立根因：本地 PM2 进程树终止曾造成过进程级掉线；此外微信服务端确实会在主进程存活时撤销该账号的桌面登录态，并明确标记为账号安全。后一事件的具体风控特征未由客户端公开，不能从现有证据继续细分为云 IP、Windows Server/虚拟显示、账号权重或自动化行为中的某一个。事件前约 50 秒 bridge 曾执行一次 wx4py 连接检查，且账号刚经历多次受控重启/重登，这些是合理混杂因素，已通过默认关闭后台自动恢复来消除，等待下一轮 A/B 验证。

这里的“多次重启/重登”仅指当晚 03:13—03:19 为验证 PM2 `treekill` 所做的受控实验，并不代表已经证明此前每晚都存在同样的密集操作。旧版 bridge 的后台检查确实固定每 5 分钟运行，异常时允许白屏硬恢复；无时间戳的历史日志确认至少发生过两次 kill + relaunch，但无法归属到具体日期或证明每次凌晨掉线前都发生。反过来，02:50—03:10 在旧版 5 分钟检查仍运行时微信保持正常，也说明单次后台检查本身不足以解释掉线。因此密集重启/重登只能作为 03:25 已捕获安全踢线的混杂或触发候选，不能作为原始“多晚约 3 点掉线”的已证实根因。

## 历史日志反查：03 点更可能是首次发现时间

继续反查远端 `wx-bridge-out.log` 后得到比单晚实验更强的长期证据。服务器安装的 wx4py `window.py` 中，`未检测到 MainWindow，使用当前窗口` 这条警告只有一条可达路径：UIA 先实际找到名为 `进入微信` 的按钮、执行点击，再等待主窗口超时。因此可用这条仅保留时间戳的日志作为“当时处于需要进入微信的登录界面”的脱敏代理证据。

- 2026-06-07—2026-07-10：34 天中 33 天出现该路径，比例 97.06%。
- 2026-08-08—2026-08-29：22 天中 20 天出现该路径，比例 90.91%。
- 合计 56 天中 53 天；首次出现时间范围 03:06—03:42，中位数 03:14。
- 统计只输出日期和时间，不保留联系人、目标或消息正文；可由 `tools/analyze_historical_login_prompts.py` 复算，结果保存于 `docs/evidence/wechat-login-prompt-history-2026-06-to-08.json`。

这排除了“2026-08-30 当晚受控实验造成的密集重启/重登，是长期每日问题的必要原因”：相同登录页路径在实验前已经高频持续数十天。此前将这些记录称为“当天首次建立 wx4py 会话”并不严谨：bridge 会长期缓存 `_wx`，没有 bridge 重启或缓存失效就不存在每日“首次”的概念。

将 53 次登录页记录与 PM2 daemon 生命周期逐次关联后，事件前 1 小时内 bridge 重启为 0 次；事件发生时 bridge 已运行的中位时长约 231.05 小时，最长约 737.24 小时。因此每晚 PM2 重启 bridge 已被排除。历史日志的实际顺序是：wx4py 开始建立/重建客户端后约 0.3—0.5 秒即识别到已经存在的 `进入微信` 界面；从 2026-06-08 起使用的自动恢复代码又会在实时 HWND 与缓存 HWND 不一致或缓存 HWND 已失效时执行 soft-rebind，主动清空并重建 `_wx`。这说明历史上的新连接主要是登录态已经丢失、窗口已切换后的检测/恢复结果，而非“重新登录”，也不能作为掉线起因。

旧日志没有全天被动 UI 采样，仍不能把历史踢线精确到分钟；2026-08-30 的 03:25:46 是首个真正逐 15 秒捕获的服务端撤销事件。该事件前约 50 秒确实发生过一次 wx4py 连接检查，因此只对这一次事件保留“连接检查可能参与触发”的候选，不能用它解释此前 53 个夜晚。

当前最关键的判别问题因此收敛为：关闭后台恢复、禁止进程终止并保持同一 IP/会话/显示后，登录态是否仍会在任何新的 wx4py 连接、重建或发送 **之前**自行变为安全弹窗。若先掉线，主因落在账号/设备/云环境风控；若每次都在明确的自动化交互之后才掉线，自动化交互才成为主触发候选。

## 发送成功误判（2026-08-30 白天补充）

用户重新认证后，数据库把 08:00、10:00 和 11:00 的任务记录为成功并推进到下一次，但用户侧未观察到实际发送。对齐 Node 与 Python bridge 日志后确认这是独立的软件缺陷：bridge `/send` 仅把发送函数放入后台队列，就立即返回 `success:true`；Node `taskQueue` 把“已入队”误当成“已发送”。10:00 和 11:00 的 5 个任务在 bridge 后台实际发生 10 次 `Send aborted`（每个任务内部重试一次），但 Node 已提前写入成功。

同时，08:20 人工重新登录后微信主窗口 HWND 已更换，后台自动恢复关闭使 bridge 继续持有掉线前的 wx4py/UIA 缓存。发送时虽然找到了新窗口，`send_to` 仍使用旧 UIA 会话，搜索/定位失败；被动监控也在 10:00:15 从 `ok` 变为 `window_hidden`，随后为低节点 `unknown`。

已实施两项修复：Node 在 `/send` 返回异步任务 ID 后轮询 `/task/<id>`，只有后台结果严格为 `true` 才标记成功；bridge 发送前比较实时 HWND 与缓存 HWND，仅在实时窗口被验证为已登录主界面时执行安全 soft-rebind，登录页或安全弹窗则直接失败，绝不自动点击。修复后只重启 `wx-schedule` 与设置了 `treekill=false` 的 `wx-bridge`，微信主 PID 保持不变。为避免重复发送，当天已被误记成功的任务不自动补发；下一次自然任务用于验收真实成功/失败回传。

15:50 后对持续低节点 UIA 状态做了一次用户授权的受控微信客户端重启。登录态自动恢复且主界面一度为 `ok`，随后微信“新版本”窗口遮挡主界面，使 bridge 只能看到 18 个更新弹窗节点。bridge 已增加严格白名单处理：只有同时验证“新版本”“更新”及 `mmui::UpdateWindow` 后，才允许选择“忽略本次更新”或“稍后处理”，绝不触发“更新”。关闭弹窗后主界面恢复为 `ok`。

连续部署期间还发现 `pm2 restart wx-bridge --no-treekill` 会在 Windows 上留下旧 `bridge.py` 监听者；一度有两个 Python PID 同时监听 `127.0.0.1:39800`，请求会随机落入旧代码。这解释了新恢复路由和新弹窗逻辑曾间歇性不生效。最终处理为：删除 PM2 的 `wx-bridge` 项、精确清理所有命令行为该 `bridge.py` 的 Python 进程，再用 `treekill=false` 重建单一实例。验收时 PM2 PID 与唯一监听 PID 均为 9604，微信主 PID 9404 未变，`/deep-health` 与 `/status` 都返回主界面 `ok`。后续不得用普通 `pm2 restart` 更新 bridge；应使用“PM2 delete → 精确清理 bridge.py → PM2 start”的单实例流程，且不能按进程名批量结束 Python 或微信。

## 优化与 A/B 顺序

1. 保持三个门禁关闭，并保持 bridge 的 `treekill=false`；当前安全弹窗已封存，不由程序自动点击。
2. 用户重新登录后，在同一服务器、同一公网 IP 下连续观察至少 3 晚；期间不重启微信/bridge、不启用后台自动恢复，只在任务真正到期时才使用 wx4py。若稳定，说明频繁恢复/重登是主要触发候选。
3. 将云主机升级到至少 4GB；若成本允许优先 8GB。升级前后保持微信版本、IP和自动化负载不变。
4. 若同一安全提示仍在约 03:00 复现，用官方微信、固定住宅/办公宽带的实体 Windows 小主机做至少 3 晚对照，保持账号、版本和任务负载不变。服务器仍掉而实体机稳定时，才把云机房 IP/Server/虚拟显示环境列为主要原因。
5. 若两边都掉，按账号级风险处理：核对手机端已登录设备与安全提醒，退出其他 PC 登录，暂停自动化数日并联系微信官方支持。
6. 若后续捕获进程停止：继续以 WMI、4688、WER 和控制审计确定杀手/退出码。
7. 若捕获显示或会话变化：统一为单一 1920×1080 虚拟显示，避免 RDP 登录/注销切换控制台；必要时使用合规的虚拟显示驱动或实体 HDMI dummy plug。
8. 将 SSH、RDP、VNC 管理端口在云安全组限制到可信来源 IP 或 VPN，并轮换管理员凭据。实施前必须确认备用入口，避免锁死运维通道。

普通反向代理不能代理微信客户端的任意主动长连接；强行使用代理会引入 IP/地域漂移，降低证据质量，也可能增加账号安全风险。本调查不采用代理或设备参数伪造作为首选方案。
